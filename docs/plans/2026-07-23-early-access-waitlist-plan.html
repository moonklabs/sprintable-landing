Part 1한눈에

목표 한 줄: 이미 완성된 waitlist 인프라 위에, ① early access 전환 서사 ② 추천 루프 ③ 운영 루틴을 얹어 waitlist 등록 수를 최대화한다.

범위: 코드(랜딩 서사·referral·OG) + 운영 가이드 문서. 콘텐츠 동결은 해제 — 이제 카피가 전환 도구다. 디자인 시스템(아이보리·네이비·명조·골드)은 그대로 유지.

A1~A4는 병렬 가능. 런치는 사용자 액션(Tally 폼 발행)에 게이트가 걸려 있다.

가장 중요한 사실 하나: 지금 이 순간 배포하면 모든 CTA가 "unavailable" 안내 다이얼로그로 떨어진다. Tally form ID가 비어 있기 때문이다. 코드 작업과 무관하게 런치 블로킹 체크리스트의 폼 발행이 최우선 크리티컬 패스다.

Part 2배경 — 무엇이 이미 되어 있고, 무엇이 문제인가

커밋 c197b42(Add localized waitlist conversion flow)로 전환 인프라는 이미 완성됐다. 상세는 원문 Context ↗ 참조.

현재 완성된 전환 파이프라인
CTA 6곳 클릭nav·hero·pricing·final·mobile
→
Tally 팝업 오픈waitlist-popup.tsx
→
히든 필드 자동 주입originPage·ctaSource·plan·UTM 5종
→
GA4 퍼널 이벤트clicked→opened→submitted
CTA는 data-waitlist-cta 속성 하나로 위임 처리되고, pricing 카드는 plan까지 태깅된다.

인프라의 실제 모습 — 히든 필드 빌더는 UTM 5종을 URL에서 자동 수집한다:

export function buildWaitlistHiddenFields({
  pathname,
  search,
  source,
  plan,
}: WaitlistContext): Record<string, string> {
  const params = new URLSearchParams(search);
  const fields: Record<string, string> = {
    originPage: pathname,
    ctaSource: source,
  };

  if (plan) fields.plan = plan;

  for (const key of CAMPAIGN_FIELDS) {
    const value = params.get(key);
    if (value) fields[key] = value;
  }

  return fields;
}

i18n 라우팅(/ko /en) + sitemap + Tally 폼 스펙 문서(docs/waitlist-setup.md)까지 갖춰져 있다. 그런데 네 가지가 비어 있다:

#남은 문제성격
①Tally 폼 미발행 — NEXT_PUBLIC_TALLY_WAITLIST_FORM_ID 빈 값 → 전 CTA가 unavailable 폴백런치 블로커 (사용자 액션)
②페이지 서사가 여전히 "제품 소개 + 요금제" — early access를 신청할 이유가 화면에 없음코드 (A1)
③추천(referral) 루프 부재 — 등록자가 다음 등록자를 데려올 장치 없음코드 (A2)
④운영 루틴 미정 — 리드가 들어와도 누가 언제 어떻게 초대하는지 없음문서 (B)
NEXT_PUBLIC_* 은 빌드 타임에 박제된다

Tally form ID는 클라이언트 번들에 임베드되는 환경변수다. Cloudflare Pages에 값을 넣어도 재배포(재빌드) 전에는 반영되지 않는다. 폼 ID를 바꿀 때마다 새 빌드가 필요하다는 점을 운영 체크리스트에 명시한다.

Part 3핵심 결정

네 가지 방향 결정이 이 플랜의 뼈대다. 앞의 두 개는 사용자가 직접 확정했다.

결정

얼리 액세스 신청자에게 무엇을 약속하나?

우선 온보딩(코호트 초대) + 파운더 직접 지원 채널 + 로드맵 우선 반영

가격 훼손 없이 신뢰 서사("검증된 것만 배포")와 일치하는 혜택. 얼리버드가 아니라 얼리 파트너로 포지셔닝.

  • 얼리버드 할인 — 전환율은 높지만 가격 앵커가 낮아진다
  • 무료 기간 제공 — 훅은 강하지만 비용 부담 + 무료 사용자 비율 증가
결정

오픈소스 셀프호스트 경로(GitHub)는?

그대로 열어둠 — nav·hero secondary·footer의 GitHub 링크 유지

오픈소스 신뢰가 브랜드 핵심이고, OSS 셀프호스트 유저가 waitlist의 잠재 풀이 된다

  • waitlist 일원화 — 리스트는 커지지만 오픈소스 서사와 충돌
결정

waitlist 백엔드는 자체 구현인가 Tally인가?

Tally 팝업 유지 (c197b42에서 이미 선택된 구조를 승계)

방문자가 캠페인 페이지를 떠나지 않고, 백엔드·개인정보 보관 표면이 생기지 않으며, 질문·라우팅·땡큐 카피를 마케팅이 코드 배포 없이 수정 가능

  • 자체 API + DB — 데이터 소유권은 좋지만 지금 단계에선 속도·운영 부담에서 손해
결정

희소성 연출은 어디까지?

정직한 희소성만 — "코호트 단위로 초대 중" (운영 사실 그대로)

브랜드가 "Claimed vs Verified", 즉 검증 가능한 주장을 파는 제품이다. 랜딩이 먼저 거짓말하면 서사가 무너진다

  • 가짜 대기자 카운터·마감 임박 타이머 — 단기 전환↑ 신뢰↓
  • 팝업 auto-open / exit-intent — 명시적 CTA 클릭시에만 팝업 (기존 가드레일 유지)

Part 6위험 · 열린 질문

폼 미발행 상태로 트래픽이 흐르면 전량 유실

현재 상태로는 CTA 클릭 → "unavailable" 안내만 나온다. 채널 포스팅·README 링크 등 어떤 트래픽도 폼 발행 전에 흘려보내면 그대로 유실된다. 런치 게이트를 반드시 지킬 것.

측정은 제출 기준, 클릭 기준이 아니다

CTA 클릭 수는 허영 지표가 되기 쉽다. 기존 가드레일대로 캠페인 품질 평가는 제출된 폼 + 검증된 후속 응대 기준으로 한다. GA4 전환 마킹을 waitlist_submitted에 거는 이유다.

  • 열린 질문 1 — OG 이미지: 존재 여부 미확인(?). 없으면 히어로 캡처 기반으로 1장 제작.
  • 열린 질문 2 — ref 코드 발급: 캡처만 먼저, 발급 자동화는 보류(hold). 볼륨 확인 후 재검토.
  • 롤백: 서사 전환은 messages/*.json 카피 변경이 대부분 — 문제가 생기면 해당 커밋 revert로 즉시 복귀 가능. 인프라(c197b42)는 건드리지 않는다.

Early Access Waitlist 극대화 플랜

Context

랜딩(feat/waitlist-conversion 브랜치)을 early access 방식으로 전환해 waitlist 등록을 최대화하는 것이 목표. 커밋 c197b42로 전환 인프라는 이미 완성됨:

  • Tally 팝업 통합: waitlist-popup.tsx — data-waitlist-cta 클릭 위임, unavailable 폴백 다이얼로그, a11y
  • 히든 필드 수집: waitlist.ts — originPage/ctaSource/plan + UTM 5종
  • CTA 6곳 전환 완료: nav·hero·pricing(plan 태깅)·final CTA·모바일 스티키 → "얼리 액세스 신청 / Join waitlist"
  • GA4 퍼널 이벤트: waitlist_cta_clicked → waitlist_form_opened → waitlist_submitted (tracking.ts)
  • i18n 라우팅(/ko /en) + sitemap + docs/waitlist-setup.md (Tally 폼 스펙)

남은 문제: ① Tally 폼 미발행(form ID 비어있음 — 지금 모든 CTA가 "unavailable" 다이얼로그로 떨어짐) ② 페이지 서사가 여전히 "제품 소개+요금제"라 early access 전환 서사가 약함 ③ 추천(referral) 루프 부재 ④ 운영 루틴 미정.

확정된 방향 (사용자 결정):

  • 혜택: 우선 온보딩 + 파운더 직접 지원 + 로드맵 반영 (할인/무료 없음 — 가격 앵커 보존)
  • 오픈소스 셀프호스트 경로(GitHub)는 그대로 열어둠 (OSS 신뢰 = 브랜드 핵심, OSS 유저가 waitlist 잠재 풀)
